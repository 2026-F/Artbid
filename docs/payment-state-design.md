# 결제 상태 설계와 회의 전 검증 범위

작성일: 2026-09-24. 담당: 이혜령. 회의에서 검토할 초안이며 팀 확정 사항은 아니다.

## 이번 변경의 목적

기존 PaymentService.pay()는 비어 있다. API를 연결하기 전에 개별 결제 시도의
상태 규칙부터 코드로 검증한다. 이번 변경은 Payment 엔티티와 단위 테스트이며,
실제 결제 API나 중복 결제 방지가 완성된 것은 아니다.

## 선택한 규칙

| 현재 상태 | 입력 | 결과 |
| --- | --- | --- |
| 생성 전 | 정산 ID, 서버 정산 금액, MOCK_PG, 요청 시각 | REQUESTED |
| REQUESTED | 거래 ID와 성공 시각 | PAID |
| REQUESTED | PG의 명확한 거절 사유 | FAILED |
| PAID | 같은 거래 ID의 성공 재수신 | 최초 거래 ID와 결제 시각 유지 |
| FAILED | 같은 실패 사유 재수신 | 최초 실패 사유 유지 |
| PAID / FAILED | 확정 결과를 바꾸려는 입력 | 예외, 기존 값 유지 |

- 거래 ID는 최대 100자, 실패 사유는 최대 500자다. 빈 값은 받지 않는다.
- 금액은 양수 원 단위 Long으로 다룬다. Payment.request()는 전달된 금액의 출처를
  검증할 수 없으므로 다음 서비스 단계에서 DB 정산 금액을 전달해야 한다.
- 시각은 호출자가 전달해 테스트에서 고정할 수 있게 했다. 기존 코드에 맞춰
  LocalDateTime을 유지한다. 실제 연동 전 저장 시간대와 API 응답 시간대를 합의한다.
- 실패 후 재시도는 새로운 Payment로 남긴다. 같은 시도의 실패를 성공으로 덮어쓰지 않는다.
- 타임아웃은 거절이 아니다. markFailed()를 호출하지 않고 REQUESTED를 유지한다.
  PG 성공 후 DB 결과 저장 실패도 결과 재확인이 필요하다.
- 결과 불명인 요청을 자동으로 FAILED로 바꾸거나 새 결제로 재시도하지 않는다.
  다음 단계에서 기존 거래 조회 및 복구가 필요하다.

payment.domain.PaymentStatus는 개별 시도의 상태다. 기존
settlement.domain.PaymentStatus는 정산 엔티티에서 사용하는 별도 상태이며 이번에는 변경하지 않는다.

## 다음 서비스 단계 설계

1. 짧은 DB 트랜잭션: 정산 행 잠금, 낙찰자/기한/정산 상태 검사, 기존 결제 시도 확인,
   REQUESTED 생성 후 커밋. 금액은 정산에서 가져온다.
2. DB 트랜잭션 밖: 모의 PG 호출. 첫 단계에서 생성한 시도 식별자를 PG 요청과 연결한다.
3. 짧은 DB 트랜잭션: 같은 정산 행 잠금, 결제 상태 재확인,
   결제 결과 및 정산의 결제 상태를 함께 저장한다.

동일 정산에 REQUESTED 또는 PAID가 있으면 새 PG 호출을 막는다.
개별 엔티티의 메서드만으로 여러 서버/트랜잭션 사이의 중복 결제를 막을 수는 없다.
위 잠금과 상태 확인은 아직 구현하지 않았다. PG 지연은 락과 커넥션을 점유한 상태로 기다리지 않는다.
큐는 이 구조의 정확성 및 부하 측정 이후 필요성을 판단한다.

전체 순서를 조율하는 PaymentService에는 트랜잭션을 걸지 않고,
별도 PaymentTransactionService의 시작/결과 반영 메서드에 적용할 계획이다.
같은 클래스 내부 호출에 @Transactional만 붙여 트랜잭션이 분리된다고 가정하지 않는다.

## API 및 회의 확인 사항

- 공개 API는 결제 요청 POST와 상태 조회 GET 두 개를 기준으로 한다.
- 기존 명세 POST는 REQUESTED를 반환한다. 동기 모의 PG 처리 후 최종 상태를 반환하도록
  바꿀지, 별도 완료 처리로 기존 명세를 유지할지 합의가 필요하다.
- 낙찰 확정 후 정산 생성 담당과 낙찰자/금액/수수료/배송비/기한 전달 계약을 정한다.
- /api와 /api/v1, Long ID와 문자열 ID 차이는 이번 변경에서 바꾸지 않는다.
- 기존 공통 예외 처리기는 IllegalArgumentException을 404로 처리한다.
  API 연결 시 입력 오류 400, 상태 충돌 409, 권한 403 등으로 구분해야 한다.
- 새 상태/시각 필드는 기존 DB 행에는 없다. 기존 결제 데이터가 있다면
  실제 상태 확인과 데이터 보정 계획이 필요하다. 일괄 REQUESTED 처리하지 않는다.
- method를 String에서 enum으로 바꿨다. 저장 표현은 문자열 MOCK_PG이며,
  기존 데이터에 다른 값이 있는지 API/DB 통합 전에 확인한다.
- 환불, 판매자 지급 배치, 자동 재낙찰은 별도 후속 범위로 논의한다.

## 테스트 실행

Java 17에서 backend 디렉터리 기준:

```powershell
.\gradlew.bat test --tests com.artbid.payment.domain.PaymentTest
```

JUnit 단위 테스트이며 Spring 컨텍스트, PostgreSQL, Redis, PG 연결은 사용하지 않는다.
초기 Gradle 및 의존성 다운로드에는 네트워크가 필요할 수 있다.
생성/성공/실패, 결과 재수신, 확정 상태 변경 차단, 잘못된 입력 시 상태 보존을 검증한다.

이 테스트로 검증하지 않는 것: JPA 저장/조회, DB 마이그레이션, 동시 요청, PG 호출 횟수,
권한, HTTP 응답, 장애 복구. 이후 PostgreSQL 통합 테스트에서 별도로 확인해야 한다.

2026-09-24 검증 결과: Java 17 / Gradle 9.6.0에서 PaymentTest 20건 통과,
실패 0건, 오류 0건, 건너뜀 0건. 전체 소스와 테스트 소스 컴파일도 통과했다.
외부 인프라가 필요한 기존 Spring 통합 테스트는 이번 실행 대상에 포함하지 않았다.

## 슬랙 공유 초안

결제 상태 규칙을 먼저 구현했습니다. 요청 후 성공/명확한 실패로 확정하고,
같은 결과 재수신은 최초 값을 유지하며 뒤늦은 다른 결과는 덮어쓰지 않도록 했습니다.
타임아웃은 실패로 확정하지 않는 방향입니다.
이번 테스트는 엔티티 규칙만 확인하며, DB 중복 결제 방지는 다음 작업입니다.
회의에서 낙찰→정산 생성 담당, 결제 POST 응답 방식, 다음 검증 일정을 맞추고 싶습니다.
