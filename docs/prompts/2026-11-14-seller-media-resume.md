# 판매자 작품 조회와 미디어 업로드 재개

- 작성일 2026-11-14
- 관련 이슈 [Artbid #130](https://github.com/2026-F/Artbid/issues/130), [frontend #69](https://github.com/2026-F/frontend/issues/69)

## 목적

판매자가 본인 작품 목록에서 기존 작품과 미디어를 확인하고 업로드를 이어갈 수 있게 한다.

## 핵심 요청

판매자가 내 작품 목록에서 기존 작품을 선택하고, 등록된 미디어를 확인한 뒤 업로드를 추가할 수 있도록 백엔드와 프론트를 구현한다. 화면을 나갔다 돌아와도 같은 작품에서 이어가며, 본인 작품만 관리할 수 있어야 한다. 업로드 완료 처리에 실패하면 파일을 다시 전송하지 않고 완료 요청만 재시도하고, 같은 요청이 반복돼도 미디어를 중복 등록하지 않는다.

## 선택과 이유

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 조회 경로 | 판매자 전용 목록·상세 API 추가 | 인증된 소유자를 기준으로 비공개 작품도 조회한다. |
| 목록 구성 | 기존 페이지 응답 조립 재사용 | 작가명·대표 이미지·연결 경매 ID를 일괄 조회한다. |
| PR 구성 | 백엔드 조회·완료 재시도를 하나로 구성 | 사용자가 연속된 백엔드 작업을 한 PR로 검토하기로 선택했다. 프론트는 목록 화면과 업로드 복구로 나눈다. |

## 반영 내용

판매자 조회 API와 업로드 완료 재시도를 함께 구현했다. 시작 기준은 원격 develop의 20f9ee7이며 브랜치는 feature/130-seller-artwork-media-resume다.

| API | 계약 |
| --- | --- |
| GET /api/artworks/mine | 본인의 모든 상태 작품을 ID 내림차순 조회. page 기본 0, size 기본 20·최대 100. 기존 페이지 응답 사용 |
| GET /api/artworks/mine/{artworkId} | 소유권 확인 후 기존 작품 상세와 미디어 응답 사용 |

비로그인은 401, 판매자 외 역할·타인 작품 접근은 403, 없는 작품은 404를 반환한다. 소유자 ID는 인증 정보에서 가져온다.

완료 API는 작품 행 락을 트랜잭션 커밋까지 유지한다. 기존 미디어의 url·sourceUrl에 같은 객체가 있으면 등록을 재사용하고, 유형이 다르면 409를 반환한다. 영상의 변환 완료 후에도 원본 URL을 기준으로 중복을 판별한다.

## 검증

- 격리된 로컬 PostgreSQL의 artbid130 DB와 Redis에서 실제 API를 실행했다. 실제 가입·로그인과 작품 등록 API로 판매자 A/B 및 일반 회원, A의 작품 21개를 준비했다.
- 테스트 DB에서 심사 대기·반려·프리뷰·경매 중·낙찰 완료 상태를 구성했다. 전체 상태 조회, 두 번째 페이지, ID 내림차순, 총 21개, B의 빈 목록, A의 비공개 상세와 media 응답 형식을 확인했다.
- 실제 요청에서 비로그인 401, 일반 회원 및 타인 상세 403, 없는 작품 404를 확인했다. 업로드 URL 발급과 완료 요청도 타인 403·비로그인 401을 확인했다.
- MinIO 배포 이미지·실행 파일에 접근하지 못해 공식 태그 `RELEASE.2025-04-22T22-12-26Z`를 Go 1.24 컨테이너에서 빌드했다. 로컬 전용 포트로 실행했으며 제품 의존성이나 배포 설정은 변경하지 않았다.
- 서명 URL 발급 → PNG PUT → 완료 요청 → 상세 조회 → 공개 URL GET을 통과했다. 저장된 파일이 원본과 바이트 단위로 일치했다.
- 첫 완료 응답을 사용하지 않고 같은 객체의 완료를 8번 동시에 재시도해도 미디어는 한 건이었다. 상세 재조회에서 같은 미디어 ID를 확인했으며, 같은 객체의 유형 변경은 409로 거절됐다.
- PostgreSQL 통합 테스트에서 같은 객체의 동시 완료, 다른 객체 동시 등록의 순서, 반복 재시도를 확인했다. 영상의 네 가지 변환 상태에서도 중복 등록 없이 변환 요청은 한 번만 발생했다. 이 테스트의 URL 제공자와 변환 서비스는 테스트 대역이다.
- Java 21에서 판매자 컨트롤러·서비스, 완료 재시도 PostgreSQL 통합 테스트와 기존 업로드 권한 테스트를 별도로 실행해 23건 모두 통과했다. 인증·역할·소유권·페이지 보정·응답 재사용도 검증했다.
- 전체 Gradle build는 461건 중 430건 통과·31건 건너뜀으로 성공한 실행이 있으나, 최신 재실행은 429건 통과·31건 건너뜀·기존 결제 알림 테스트 1건 실패였다. 초기 기본 DB 연결 실패는 격리 DB·Redis 연결을 명시해 해결했다.
- 변경 전 `develop`의 `20f9ee7`에서도 전체 테스트를 실행해 같은 결제 알림 테스트 실패를 재현했다. 444건 중 412건 통과·31건 건너뜀·1건 실패였으며 해당 테스트의 단독 실행은 통과했다. 요청 시각의 나노초 정밀도와 결제 처리 시각의 마이크로초 절삭 차이로 발생하며, 결제 코드와 테스트는 이번 변경에서 수정하지 않았다.

## 남은 작업

- 프론트 목록·상세 화면, 공통 업로드 UI와 단계별 실패 복구는 별도 PR로 진행한다.
- 브라우저의 사진·영상 표시와 재생, 화면 재진입, 업로드 후 목록 갱신은 후속 화면 연동에서 확인한다.
